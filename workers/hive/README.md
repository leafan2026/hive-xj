# hive 服务看板

线上地址：https://lf.run.jinapp.net/hive/

数据源：金数据表单 `EQca39`（AI 会话质检 4.0），约 6600 条会话。

## 部署

平台是 [WDL](https://wdl.dev)（自托管 Workers 运行时），跟 zlb / qa-tickets 同一个
namespace `lf`、同一个控制面、同一个部署 token。URL 形态 `https://<ns>.<platform-domain>/<worker>/`。

部署令牌只保存在本地、被 Git 忽略的 `.key` 文件中（内容仅为原始 `ADMIN_TOKEN`）。
在 `workers/hive/` 目录中确认 `.key` 已由安全方式写入后执行：

```bash
ADMIN_TOKEN="$(<.key)" CONTROL_URL="https://admin-run.jinapp.net" WDL_NS="lf" \
  pnpm dlx @wdl-dev/cli@1.7.1 deploy . --ns lf
```

部署成功会输出已 promote 的 `vN` 与线上 URL；再执行：

```bash
curl --head --fail --silent --show-error https://lf.run.jinapp.net/hive/
```

不要使用 `wrangler deploy`。凭证、提交、部署和回退的完整安全流程见仓库根目录
`.skill/hive-release/SKILL.md`。

## 本地预览

在 `workers/hive/` 目录运行：

```bash
pnpm run preview
```

打开 `http://127.0.0.1:4173/hive/preview` 即可查看合成示例数据。该预览不会读取金数据、
不会使用生产凭证，也不能触发真实的数据刷新；它只用于检查页面布局、图表和登录后的界面效果。

部署完刷缓存：登录后点页面右上角「重新拉取数据」（`POST /api/refresh` 要 cookie，
curl 裸调是 401），或等 cron 的下一个半点。

## 架构

- 金数据 API `per_page` 实际封顶 50 条/页，`next` 参数就是 `serial_number` 偏移，
  因此按偏移**并行**拉取（并发 10），全量约 13 秒；按 `serial_number` 去重
  （该表 `token` 字段多为 null，不能用作去重键）。
- 聚合结果与精简后的明细写入 KV（`hive:stats:v5` / `hive:entries:v2` / `hive:meta:v1`），
  页面只读缓存，接口响应在百毫秒级。
- cron `*/30 * * * *` 后台刷新；`POST /api/refresh` 手动触发（立即返回 202，
  进度写在 meta 里，前端轮询 `/api/status`）。

## 业务闭环（独立页签）

`field_30 业务闭环`（是/否/待定/不适用）驱动「业务闭环」页签的两张图，走 `GET /api/loop`
（`K_LOOP` 缓存，不受顶部筛选影响）。三条口径：

1. **适用会话** = 业务闭环 ∈ {是, 否, 待定}。「不适用」和空一律排除 —— 那些是非有效会话，
   或业务分型为「看不出用途」（读不出用户要办什么业务，没有闭环可测）。
2. **闭环率** = 是 ÷ **全部适用行**（是 + 否 + 待定），**下限口径**。
   上游判定：7 天窗口内收到过数据就立刻判「是」，不等窗口满；只有「窗口没满且还没收到数据」
   才留待定。待定只会往是或否落地，所以当周读数只会低估、不会高估，待定清零后这个公式
   自然等于最终闭环率 —— 一个公式同时管未定稿周和定稿周，不用换算法。
3. 周次按会话创建时间的 **ISO 周**（周一起）。待定占比 > 30% 的周，折线画成浅色虚线；
   适用会话为 0 的周直接断开，不画点。

图二与图一同口径（全部适用行进分母，含待定），按场次降序，场次 < 10 的分型排到最后并标灰，
另有一条整体闭环率的参考竖线。

口径核对（第 27~33 周，旧判定下的存量）：是 1553 / 否 504 / 待定 363 / 整体闭环率 64.2%
（旧公式 75.5%）。上游按新判定重算后 待定会大幅下降、该数会回升，届时以重算结果为准。

## 业务分型 × 建表转化（第 32 周起，已被上面的闭环图取代）

表单在 2026-08-03（第 32 周）新增了 `field_22 业务分型` / `field_23 对口建表` /
`field_24 对口scene` / `field_25 对口表单收数据` / `field_26 窗口内收款` /
`field_27 Jiri代建表单`，周报第六个板块按分型统计建表转化，分母是该分型的会话数：

- **建表率** = 「对口建表」标了`是`或`否`（都表示建了表，只是对不对口）；`待定`/`不适用`视为还没建
- **对口** = 「对口建表 = 是」
- **建完收到数据** = 「对口表单收数据 = 是」
- **Jiri 代建** = 「Jiri代建表单 = 是」
- 「只跟金数据打交道」「看不出用途」不是建表需求，不计入

只有标注过的周才显示这个板块（`bizTypes` 为空时整块隐藏）。每格下面带环比 / 同比，
口径与其他板块一致（对齐相同星期）。注意「待定」还很多（7 天窗口未到或待复核），
数字会随标注推进变化。

## 周报口径（表单字段有坑，已核准）

`/api/weekly` 按 ISO 周输出周报表格，默认展示**本周**（weeks 里只有有数据的周，
所以最后一项就是本周；本周还没数据时自然落到上周），不完整的周会在下拉里标注。口径按第 30 周的
人工周报逐项反推核准，12 个场景 × 5 个指标完全一致：

- **有效人工** = 处理状态「仅人工」且会话性质「有效」。周报里说的「143 个 id」实际是
  **会话数**，不是去重用户数（同周去重用户只有 123）。
- **接待次数**取 `field_13 转人工会话接待次数`。`field_20 人工接待次数` /
  `field_21 人工接待次数-有效` 这两个字段**全表为空**，不能用。
- **单次中位** = 每场「时长 ÷ 接待次数」的**中位数**（不是每场时长的中位数）。
- **单次平均**：总表用「总时长 ÷ 总接待次数」；场景表用每场「时长 ÷ 接待次数」的
  **算术平均**（两处口径不同，与人工周报一致）。
- **AI 独立率** = 处理状态「仅 Jiri」的会话数 ÷ 全部会话数（顶部卡片和周报同口径）。
- **业务场景**相关的图表与交叉表都只算**会话性质=有效**的会话；未质检的会话场景为空，
  会聚成一个「未分类」把其他项压没。
- **套餐**字段为空视为**免费版**。
- **目标值**为常量：操作引导类人工时长占比 ≤10%；必处理场景单次中位数
  故障 ≤9 / 财务(账务) ≤6 / 申诉 ≤4 / 收款 ≤5 / 实名 ≤2 分（第 21 周基线下降 30%）。
- 周报数据独立于顶部筛选栏（走 `K_WEEKLY` 缓存），筛选不影响它。

## 筛选

页面顶部筛选栏对**全部卡片和图表**生效（默认过去 14 天）：时间范围、设备、业务场景、
会话性质。接口仍支持 `channel` / `status` / `plan` / `qc` 参数，只是页面上不再暴露。

时间范围支持相对区间（过去 7 / 14 / 30 / 60 / 90 / 365 天）、自然周期（本周 / 上周 /
本月 / 上个月 / 本季度 / 上季度 / 本年 / 去年）和自定义起止日期。区间在服务端按
**东八区当天**换算成 `from` / `to`，前端只回显结果 —— 前端不需要先知道数据里的最新日期。筛选走服务端 —— 无筛选时命中预聚合
缓存，有筛选时读 KV 明细现算，都在 200ms 量级。下拉选项只在首次全量结果时填充一次，
否则筛完选项会跟着缩水。

## 周度接待概览的环比口径

表格只显示到所选周为止的**最近 5 周**（周数增长后自动滚动，不会一直堆着旧周）。
底部两行是「上周同期」与「环比」：本周若只跑到周四，就拿上周的**周一~周四**对齐着比 ——
天数不同没法比。对齐在服务端做（`compare.dows` / `compare.prev`），因为「对话人数」
是去重值，不能把每天的去重数相加。

三、四、五三个板块用同一套对齐口径：三在底部按口径给出「上周同期 / 环比 / 4 周前同期 / 同比」，
四、五在右侧加环比与同比列（四比总时长，五比场次）。

同比用 **4 周前的同一批星期**（本周第 31 周 → 对比第 27 周）—— 数据不足一年，
没有真正的去年同周可比，4 周前能大致避开单周波动。

## 指标口径

### 24 小时服务节奏

服务概览底部的小时图只展示当前筛选结果中最近 7 个自然日，默认选中最新一天；日期标签一次只展示一天，避免多天多指标叠在一起难以阅读。横轴每个点覆盖该小时的 `00:00–23:59` 分段：

- **Jiri 会话量** = 处理状态「仅 Jiri」的会话数。
- **人工会话量** = 处理状态「仅人工」的会话数。
- **人工会话时长** = 处理状态「仅人工」且有时长记录的总时长。

小时按金数据记录中的原始日历时间划分，与现有按天统计口径一致。

### 人工服务忙闲分布

服务概览底部的忙闲图同样只展示当前筛选结果中的最近 7 个自然日，横轴固定为每天
`09:30–19:00`，每格为 15 分钟。它用于判断人工服务的高峰时段：

- **同时服务人数**：处理状态为「仅人工」且有人工接待时长的会话，按「记录时间 + 人工接待时长」
  落入所覆盖的每个 15 分钟；每格显示该段正在由人工接待的会话数。
- **新转人工人数**：处理状态为「仅人工」且记录时间落在该 15 分钟的会话数。
- 图表底部用一句话提示最近 7 天内的**最忙高峰**和**次高峰**，数值为对应 15 分钟的日均人数。
- 没有人工服务的时段直接留白；整天都没有人工接待的日期不显示。

表单目前没有「人工真正接手的时间」字段，因此图中以会话记录时间作为人工服务开始时间；
它适合判断排班趋势，不应用作逐分钟的人工响应时效核算。

`Jiri是否能解答` / `转人工方式` / `转人工原因` 只在人工质检过的会话上有值
（约 764 条，占 11.6%），AI 相关指标按这批口径计算，未打标记录不参与，
避免被稀释。会话性质、渠道、场景等字段全量有值，按全部会话计算。

## 接口

| 路径 | 说明 |
|---|---|
| `GET /` | 看板页面 |
| `GET /api/dashboard` | 聚合指标。无参数时返回预聚合缓存；带筛选参数（`from` / `to` / `channel` / `device` / `status` / `scene` / `nature` / `plan` / `qc`）时读明细现算，约 200ms |
| `GET /api/entries` | 明细，支持 `page` / `per_page` / `channel` / `scene` / `nature` / `jiri` / `search`（接口保留，页面已不展示明细） |
| `POST /api/refresh` | 触发后台全量刷新 |
| `GET /api/weekly` | 按周的周报数据（目标追踪、接待概览、人工场景工作量、仅 Jiri 场景） |
| `GET /api/status` | 刷新状态与数据更新时间 |

## Secrets

| 名称 | 用途 |
|---|---|
| `JSJ_API_KEY` / `JSJ_API_SECRET` | 金数据 API 凭证 |
| `AUTH_USERS` | 登录账号，格式 `user1:pass1,user2:pass2`；生产环境必须配置，缺失时服务拒绝访问 |

## 登录

自带登录页（`GET /` 未登录时返回），提交到 `POST /api/login` 校验 `AUTH_USERS`，
通过后下发 HMAC 签名的 `hive_session` Cookie（HttpOnly + Secure + SameSite=Lax，7 天）。
签名密钥由 `AUTH_USERS` 派生 —— **改动账号会让所有已有会话失效**。顶栏显示当前账号，
「退出」调 `POST /api/logout` 清 Cookie。

**页面只认会话 Cookie**，`Authorization: Basic` 只对 `/api/*` 生效（方便 curl 调试）。
这一点是必须的：浏览器会把曾经在原生登录框里输过的 Basic 凭证一直自动带上，如果页面
也认 Basic，「退出」清掉 Cookie 后仍会被放进来，表现就是点了退出没反应。

服务端不返回 `WWW-Authenticate`，所以浏览器不会弹原生登录框；接口未登录统一返回
`401 {success:false, login:true}`，前端收到后自动跳登录页。
